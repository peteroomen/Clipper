# Undo ring over rig state + a cancellable assistant turn

**Date:** 2026-07-25
**Branch:** feat/undo-ring
**Roadmap item:** 2026-07-24 audit, UI/UX findings 2 and 3 — "Remove and Swap are instantly
destructive with no undo anywhere in the project" and "Assistant tool calls rearrange the live
rig with no cancel and no undo". Also unblocks the CLAUDE.md rule "Destructive actions (remove
pedal, swap pedal) need an undo path. There is none today — don't add more destructive surface
without one." Docs §39, ADR 011.

## Goal

Every rig-changing action in the web app is undoable (Cmd/Ctrl-Z, plus a visible, keyboard-
operable Undo/Redo pair), an assistant turn is **one** undo unit, and a turn in flight can be
**cancelled** without the chat input losing focus.

## Approach

**Model: a bounded ring of `serializeRig()` snapshots, held in a ref, restored through
`deserializeRig()`.**

- The rig-state JSON is already the canonical serialization (`web/src/rig.ts`), so a snapshot
  ring is the cheap path: no per-action inverse operations to write and keep in sync with six
  pedal types, four amps and the chain editor. The cost is memory per entry (measured below)
  and that a snapshot restore is a *whole-rig* push to the engine (one declick fade), not a
  surgical one.
- Snapshots are stored as **strings**, not objects: immutable (a later mutation of live state
  cannot corrupt history), trivially measurable, and — the load-bearing part — a restore goes
  back through `deserializeRig` → `normalizeRig`, the same validation an untrusted persisted
  rig gets. Non-finite and out-of-range values cannot re-enter the engine through the undo
  path.
- The ring lives in a **ref**, not React state. A knob drag must not re-render the app more
  than it already does, so `record()` takes a *thunk* and only calls `serializeRig` when it
  has actually decided to push. The only React state is the top entry's label, which changes
  at most once per coalesced group.

**Coalescing.** `record(label, key)` where `key` is a coalescing key (`p:<pedalId>:<param>`,
`amp:<param>`, `input:trim`). If the incoming key equals the last-pushed key and the last push
was within `COALESCE_MS`, the push is *dropped* (the older entry is the true pre-drag state)
and the window is extended. Discrete actions (stomp, toggle, chain edit, amp/cab swap) pass
`key = null` and never coalesce — two consecutive toggles must be two undos, or an undo appears
to do nothing.

**One assistant turn = one undo entry.** `begin(label)` / `end()` on the ring: `begin` captures
the pre-turn snapshot and suppresses all pushes inside the transaction; `end` pushes that one
snapshot **only if the rig actually changed**. So a text-only reply and a cancelled turn leave
no entry, and a 2-tool-call turn is one entry — undoing can never land the rig in a half-applied
state the player never saw.

**Cancel.** A real `AbortSignal` threaded through `runAssistant` → `requestTurn` → `fetch` and
checked before tool execution, so a cancel mid-stream never applies that turn's tool calls. On
abort the partial turn is discarded from the API history (an assistant `tool_use` with no
`tool_result` would 400 the next request).

**Focus.** The chat input stops being `disabled` while busy (that is what drops focus to
`<body>`) and becomes `readOnly` + `aria-busy`. The send button turns into a **Stop** button
while busy rather than being disabled, so neither element ever leaves the a11y tree mid-turn.

**Redo is IN scope** — an undo with no redo is itself a destructive action. Any new record
clears the redo stack.

## How this will be measured

1. **Coalescing:** a real 3-second pointer drag on a knob. Report `attempts` (what a naive
   one-entry-per-change ring would have pushed) → `pushed` (what the coalescing rule pushed),
   plus `serializations` (proof the dropped pushes cost no `JSON.stringify`).
2. **Memory:** exact bytes per entry, measured with `TextEncoder` (UTF-8) and `json.length * 2`
   (the JS string's UTF-16 footprint), for a default rig and a worst-case 8-pedal rig, times
   the ring capacity → the total bound. Asserted against a hard ceiling in the test.
3. **Player-observable Playwright assertions** (never an identity):
   - dial three knobs on a pedal, swap the pedal for another type, undo → the *dialled-in
     numbers* are back on the *original* pedal type and id
   - remove a dialled-in pedal, undo → it is back, with its values
   - an assistant turn making **two** tool calls, one undo → the pre-turn rig, and the ring
     depth proves it was one entry, not two
   - start a turn against a hanging `/api/chat`, cancel → the rig is byte-identical to before
     and `document.activeElement` is still the chat input (not `<body>`)
   - a hostile snapshot injected into the ring restores **clamped** (proves the undo path
     re-validates rather than trusting the stored JSON)
   - redo restores the undone state; Cmd/Ctrl-Z works from the keyboard

- [ ] Edge: undo past the oldest entry → the button is disabled, nothing happens

## Out of scope for this session

- **Named presets / save slots** (the other half of the "Presets & sharing" deferred item)
- **Persisting the ring across a reload** — the ring is in-memory; a reload is a history
  boundary. Persisting it means a second storage key and a size budget; not today.
- **Undo for things outside the rig JSON**: the custom-IR *samples*, the guitar profile, the
  theme, engine start/stop, and the chat transcript. Undoing an IR *upload* restores the cab
  *selection* only (the samples are deliberately not in the rig JSON).
- **Native (JUCE) undo** — the plugin has its own state tree; parity is its own slice.
- `web/playwright.config.ts`'s `retries: 2` (docs §29 recommendation, deliberately not changed
  unilaterally).
- Anything under `core/`, `web/worklet/`, `native/`, `web/public/generated/` — no WASM rebuild.

## What actually happened

Built as planned; three things worth recording.

**1. A real bug fell out of the design, and it was not in the audit.** `rigRef` was only written
during render, while `addPedal` / `removePedal` / `swapPedal` / `movePedal` each read it and
pushed a whole new rig object. React 18 batches, so two chain edits in one tick — exactly what
an assistant turn does — both read the pre-first-edit ref and the second overwrote the first.
"Add a Screamer and a phaser" landed **only the phaser**. Every mutator now goes through
`commitRig()` (eager ref write, then `setRig`), which also happens to be what makes an undo
snapshot taken at the top of a mutator genuinely the pre-mutation state. Pinned by the new
"two chain edits in one turn both land" test.

**2. Redundant writes had to be dropped before the ring.** A clamped drag edge or a
double-click reset of a knob already at its default calls the setter with an unchanged value.
Recording those produced undo steps that visibly did nothing, so `setPedalParamById`,
`setInputTrim` and `setAmpParam` now early-return on an unchanged value.

**3. The focus fix is the `disabled` attribute itself, not a focus-restore.** `readOnly` +
`aria-busy` on the input and a send button that *becomes* the Stop button (same DOM node, so
React reuses it and focus never leaves) fixes the cause. The `finally` block still restores
focus if it fell to `<body>` for some other reason, but the test proves focus never moves in the
first place.

Redo was kept (planned as in scope): it is ~20 lines on top of the ring and removes the
"undo is itself destructive" hole.

Two measurement notes: the drag test needed `knob.hover()` before `boundingBox()` (page.mouse
works in viewport coordinates, and the board unit is below the fold — without it the drag
dispatched 180 moves that reached nothing and measured 0 attempts, a silently vacuous test),
and the memory ceiling was set to 128 KiB after measuring 73 344 B for a full ring of 8-pedal
rigs (the first guess of 64 KiB was wrong, so the number moved, not the measurement).

## Measured results

**Coalescing — a real 3-second pointer drag (180 `pointermove` events) on the RAT's Dist knob:**

| | naive one-entry-per-change | shipped |
|---|---|---|
| undo entries pushed | **180** | **1** |
| `JSON.stringify` calls | 180 | **1** |
| ring-driven React state updates | 180 | 1 |

Raw counters over the drag: `attempts` 180, `pushed` 1, `coalesced` 179, `serializations` 1,
wall-clock 4 746 ms (an earlier run at 3 046 ms gives the same entry count). One undo returns
the knob to its pre-drag value.

**Memory — exact stored payload (`TextEncoder` for UTF-8, `length * 2` for the JS string):**

| snapshot | UTF-8 | UTF-16 (in-memory) |
|---|---|---|
| default rig (1 pedal) | 415 B | 830 B |
| 8-pedal rig (largest the UI can build) | 1 146 B | 2 292 B |
| full ring, 32 × 8-pedal | **36 672 B** | **73 344 B** |

48 discrete actions → 32 entries held, 16 evicted. Capacity 32.

**Tests:** `web/tests/undo.spec.ts` — 10 tests, all passing. `tsc --noEmit` clean, `vite build`
clean. The rest of the web suite is unchanged in behaviour; `audio.spec.ts`'s
`OfflineAudioContext` silence flake reproduces identically with this slice stashed (6 failed /
4 flaky on pristine `origin/main` vs 6 failed / 3 flaky with the slice), i.e. environmental, not
caused here.
